# TASK-004 — Add live compass course card

## Status

READY_FOR_DESIGN

## Goal

Add a foreground-only course card to the fine-location dashboard. It must show the device's current compass heading when supported and, independently, the current GPS bearing when the active location session supplies one. The card must communicate waiting and unsupported hardware truthfully rather than inventing a direction.

## Context

TASK-001 established precise-location onboarding, TASK-002 added foreground GNSS availability/status, and TASK-003 added foreground GPS speed, altitude, and vertical speed. The legacy dashboard also has a course instrument driven by device orientation sensors, with an optional bearing derived from GPS fixes. That is the next self-contained flight instrument: it reuses the rewrite's foreground lifecycle and live location path without requiring the legacy city database, route selection, osmdroid map archive, network, or background service.

The legacy course card is evidence for the desired user-visible purpose and visual language, not a mandate to reuse its service binding, animation code, preference-based card hiding, or sensor calculation literally. This task intentionally defines a simpler, accessible Compose equivalent.

## Original Application

`app/src/main/java/kniezrec/com/flightinfo/cards/adapter/CardViewContainer.kt` places `CourseCardView` near the beginning of the permission-gated dashboard. `cards/course/CourseCardView.kt`, `CourseCardViewPresenter.kt`, and `res/layout/course_card_layout.xml` show a large numeric compass course, a cardinal/intercardinal abbreviation, a compass/plane visual, and `From GPS: N°` when a location update has bearing.

The legacy sensor source is `services/SensorService.kt`; it supplies a course generated by `avionic/calculators/CourseCalculator.kt` from accelerometer and magnetic-field events. The calculator maps a normalized heading to `N`, `NE`, `E`, `SE`, `S`, `SW`, `W`, or `NW`. When the required hardware is absent, the legacy card overlays a prompt that permits hiding the card. It registers its GPS-bearings callback separately from the compass callback.

Useful legacy visual references are `res/drawable/plane_icon.xml`, `res/layout/course_card_layout.xml`, `res/values/colors.xml`, `res/values/dimens.xml`, and `promo/promo.png`. The promo PNG exists at `promo/promo.png` (1024 × 500), but it cannot be rendered in the workspace sandbox; inspectable XML/resources are the visual source of truth. `/home/ai-dev/smart-flight/lib` does not exist; the actual `app/libs/` JARs (`jsi-1.0.0.jar` and `trove4j-2.0.2.jar`) are unrelated and must not be imported.

## Current Application

The rewrite's fine-permission dashboard is assembled in `app/src/main/java/kniezrec/com/flightinfo/MainActivity.kt`. It starts and stops `GnssStatusController` and `FlightParametersController` as the activity enters and leaves the foreground. `flight/AndroidFlightLocationPlatform.kt` currently converts GPS location callbacks into speed, altitude, and elapsed-realtime data only; it does not expose bearing.

`ui/gnss/GnssStatusScreen.kt` provides the scrollable single-column dashboard and currently renders `FlightParametersCard` after the GNSS card. `ui/gnss/FlightParametersCard.kt` establishes the existing purple card, text, semantics, responsive-row, and waiting-state patterns. The rewrite has no sensor/platform adapter, orientation state/controller, or compass UI. Its minSdk is 31, and no sensor or location dependency beyond Android platform APIs is necessary.

## Functional Requirements

- With fine location granted, place exactly one `Course` card after the existing GNSS-status and Flight parameters cards. Fine permission remains the dashboard gate: approximate-only, denied, or revoked fine permission must display TASK-001 onboarding and leave no compass or bearing observation active.
- While the eligible dashboard is foregrounded, observe a device-orientation source and derive a magnetic compass heading. The heading must be normalized to an integer in the inclusive range `0`–`359`, where 0 means north.
- Render the nearest eight-point compass abbreviation using these inclusive midpoint bands: `N` for 338–359 and 0–22; `NE` 23–67; `E` 68–112; `SE` 113–157; `S` 158–202; `SW` 203–247; `W` 248–292; `NW` 293–337.
- Before the first valid orientation reading in the current foreground session, show a waiting state. Do not retain a previous-session heading or show a default 0°/N as measured data.
- When a valid heading is available, display its numeric degree value with a degree symbol and its eight-point abbreviation. The visual indication of direction must update to match the same normalized heading. The displayed course is magnetic/device heading; do not label it as GPS course, true north, or aircraft track.
- If an orientation-capable sensor source cannot be used on the device, show a stable `Compass unavailable` state that explains the device cannot provide a compass heading. Do not start sensor registration in that state and do not offer a hide-card preference or a misleading retry action.
- If a supported sensor source cannot be registered or fails unexpectedly, show `Unable to read compass`; provide `Try again`, which re-evaluates hardware availability, clears old heading/bearing data, and retries only while the dashboard is foregrounded.
- Obtain GPS bearing only from the current foreground GPS location-observation session. A GPS fix with a valid bearing updates the secondary bearing value; a fix without bearing makes that value unavailable. Do not derive GPS bearing from speed, prior coordinates, or a last-known location.
- GPS bearing is supplementary: a valid compass heading remains useful when no GPS bearing is available. If compass observation is unavailable/error, do not display a stale GPS bearing as a substitute for the compass course.
- New foreground sessions, fine-permission loss, location-services-disabled/GNSS-unavailable states, any observation-registration failure, retry, and return from system settings must clear compass and GPS-bearing values before any new current-session callback. Existing TASK-002/003 behavior remains unchanged.
- Register sensor and bearing observations only while the fine-permission dashboard is active and foregrounded. Stop/unregister all added callbacks on pause, permission loss, dashboard destruction, unavailable/error state, and before a retry/restart. Repeated lifecycle events must not accumulate listeners.
- The feature must work without internet connectivity and must not start a service, collect in the background, issue notifications, persist heading/bearing history, or request a new runtime permission.

## Technical Requirements

- Use Android platform sensor APIs supported by minSdk 31. Prefer a rotation-vector sensor when available; an accelerometer-plus-magnetic-field fallback is acceptable when it produces the same device-relative magnetic-heading meaning. Do not add a sensor, navigation, fused-location, map, or third-party compass dependency.
- Account for the current display rotation when transforming sensor orientation so the displayed heading represents the device's visible top direction in portrait and landscape. Keep sensor-framework objects behind a narrow, testable platform boundary; pure normalization, cardinal mapping, and presentation state must be framework-independent and unit-testable.
- Reuse the existing `FlightLocationPlatform`/`FlightParametersController` location callback path by extending its small framework-independent fix model with explicit nullable/valid GPS bearing data, or use an equivalently narrow shared foreground-location boundary. Do not add a second concurrent `LocationManager` listener solely for bearing.
- Treat `Location.hasBearing()` (or the platform equivalent) as the validity condition for GPS bearing. Normalize valid bearing values to the same 0–359 display convention. Do not expose Android `Location` to Compose.
- Coordinate start/stop and availability outcomes with `MainActivity`'s existing foreground lifecycle. When TASK-002 determines location services are disabled or GNSS hardware is unavailable, the course/bearing state must be reset and no GPS listener may remain active.
- All user-visible and accessibility text, degree/value formatting templates, and action labels must be Android resources. Use locale-aware number formatting. Preserve current app identity, edge-to-edge handling, and TASK-001 through TASK-003 permissions/actions.
- Do not copy the legacy `CourseCalculator` smoothing formula without validation; its implementation is not a specification. Any filtering/smoothing added for visible stability must be deterministic, bounded, documented in code, and focused-test-covered. A direct latest-valid-reading implementation is sufficient for this increment.

## UI Requirements

- Retain the existing dark-purple page/header and the centered, scrollable, maximum-600-dp dashboard column. Add the Course card after Flight parameters with the established 12 dp margins/gaps, purple `#5B5999` rounded surface, and 4 dp elevation.
- The card has a clear `Course` title. In waiting it centers `Waiting for compass heading…`; in unavailable/error states it centers the state title/body and displays the existing cyan text-action treatment only for `Try again`.
- In the available state, make the compass heading the primary information: a large degree reading plus cardinal abbreviation, accompanied by a simple plane/compass direction visual. Reuse/adapt the legacy vector plane artwork if it fits the Compose implementation; do not introduce a raster asset or external icon library solely for this card.
- Display `GPS bearing` as secondary text/value beneath or adjacent to the primary course, using `—` when the current session has not supplied a valid bearing. Its visual and TalkBack wording must make clear it is distinct from compass course.
- The direction visual must not be the sole carrier of information: the degree and abbreviation are always visible/readable in the available state. Avoid continuous decorative animation; changes may use a brief reduced-motion-respecting transition.
- Use logical start/end layout, outer-page scrolling, and a vertically expandable card so portrait, landscape, expanded windows, RTL, keyboard/switch access, gesture insets, and 200% font scale remain usable without clipping or overlap.
- Merge meaningful label/value pairs for TalkBack. Expose state changes politely without announcing every sensor update; the unavailable marker must have an explicit spoken meaning rather than being read only as a dash.

## Risks and Edge Cases

- Sensor availability varies by device; an emulator commonly has no meaningful orientation stream. The unavailable and waiting states must remain useful indefinitely.
- Magnetometer/device headings can be noisy and affected by local interference. This is an informational magnetic compass, not an aviation-certified navigation instrument; do not claim true-north correction or GPS-track accuracy.
- Display rotation changes the interpretation of sensor axes. The platform adapter must refresh/recompute correctly after configuration/display rotation changes without retaining a false heading.
- A valid GNSS fix need not include bearing, especially when stationary. Missing bearing is normal and must not be treated as a compass error.
- Existing TASK-003 location registration errors flow into the GNSS error state; course coordination must clear data and avoid turning a location failure into a false sensor error.
- Rendering and accessibility must cope with rapid updates without excessive TalkBack announcements or layout instability.
